# RoyalItems

**Give every vanilla item a name, lore, rarity, and identity — without turning it into a custom item.**

RoyalItems dresses ordinary Minecraft items (coal, a diamond sword, a raw cod) with the polished look
players expect from a SkyBlock-style server — a coloured name, descriptive lore, a rarity tier, a
rarity-coloured tooltip border — while **keeping the exact same `Material`**. A dressed diamond sword
is still a fully-functional vanilla diamond sword: it enchants, repairs, and works in every recipe and
shop exactly as before. The only things that change are what the player *sees* (lore and border) and
what a plugin can *read* (a persistent-data identity).

Built for **Paper 26.2 or newer**, Java 21. Lightweight, config-driven, and safe to run alongside
custom-item plugins like EcoItems — it never touches an item that already has an identity.

---

## Why it's different

| | Plain vanilla | A custom-item plugin | **RoyalItems** |
|---|---|---|---|
| Has lore / rarity | ❌ | ✅ | ✅ |
| Still the same Material | ✅ | ❌ (usually a re-skin) | ✅ |
| Works in vanilla recipes/shops | ✅ | ⚠️ depends | ✅ |
| Readable identity for other plugins | ❌ | ✅ | ✅ (PDC `item_id` / `fuel_id`) |

**The one rule to understand:** *identity lives in the item's persistent data (PDC); lore is only
visual.* Nothing in RoyalItems — or any plugin reading it — should ever parse lore for logic. Ask the
PDC instead.

## Features

- **A full generated catalog** — every dressable vanilla item ships pre-classified into nine by-type
  files, regenerable any time with `/royalitems export`. Hand-tuned items live in `0-overrides.yml`,
  which always wins.
- **Schema-v2 entries** — the entry key alone is enough: `rarity` + `category` drive the auto-generated
  name, lore footer and border. Override any field only where you need to.
- **Universal rarity tooltip borders** — a coloured border around the whole tooltip of *any* item on
  the server (eco gear, vanilla drops, bazaar purchases), applied on the outgoing packet from the
  item's own rarity line. Needs [PacketEvents](https://modrinth.com/plugin/packetevents); degrades
  gracefully to RoyalItems-dressed items without it.
- **Event-driven dressing** — items format the instant they are created or acquired: mined, mob drops,
  harvest, craft, smith, chest loot, furnace output, pickup, and whenever a container closes (which is
  when bought/traded items land). No polling; an optional sweep exists only as a backstop.
- **Self-healing lore** — dressing stamps a definition hash into the item; when you edit a definition,
  existing items refresh themselves through the same events, keeping enchants and damage intact.
- **Rule engine safety net** — `rules.yml` catches anything the catalog missed (or a future Minecraft
  version added) so nothing ships bare.
- **Developer API** — other plugins read a drop's identity through the Bukkit ServicesManager.

## Installation

1. Drop `RoyalItems.jar` into `plugins/` (and PacketEvents, for universal borders).
2. Start the server once — it generates `config.yml`, `rarities.yml`, `rules.yml`, and `items/`.
3. Edit to taste and run `/royalitems reload`.

## Configuration

```
plugins/RoyalItems/
├── config.yml       master switch, disabled worlds, join/sweep options, tooltip borders
├── rarities.yml     the rarity ladder (Common → Mythic) + per-rarity tooltip styles
├── rules.yml        the safety-net rule for anything the catalog misses
└── items/           the catalog (scanned recursively; explicit items always beat rules)
    ├── 0-overrides.yml   hand-tuned items — sorts first, so its ids always win
    ├── armor.yml         generated by-type files (regenerate with /royalitems export)
    ├── building.yml
    ├── decoration.yml
    ├── food.yml
    ├── materials.yml
    ├── redstone.yml
    ├── tools.yml
    ├── weapons.yml
    └── misc.yml
```

### `config.yml` highlights

```yaml
enabled: true              # master switch
disabled-worlds: []        # worlds RoyalItems ignores (by name, case-insensitive)
format-on-join: true       # dress a player's whole inventory when they join
format-sweep-seconds: 0    # optional periodic backstop; 0 (off) is right for almost everyone

tooltip-borders:           # the universal packet-level borders — see the file's comments
  enabled: true
  context-keywords: [TIER, RARITY, ROYAL]
  styles:
    COMMON: royalitems:common
    # ... one entry per rarity, naming a sprite in your resource pack
```

### `items/*.yml` — schema v2

The key is the `item_id` **and** (upper-cased) the default material. Everything else is optional:

```yaml
formatted-items:
  ender_pearl:                    # -> Material ENDER_PEARL, auto name, auto footer
    rarity: uncommon
    category: Combat Item

  coal:                           # a hand-tuned entry (0-overrides.yml)
    rarity: common
    category: Minion Fuel
    fuel: coal                    # shorthand for a fuel_id identity tag
    lore:
      - "&7Minion Fuel &8(+5% speed, 30min)"
      - ""
      - "&f&lCOMMON"
```

With no `lore:` the footer auto-fills to `&8<category>`, a blank line, and the rarity display. With no
`name:` the name auto-fills to the rarity-coloured title case of the key. `tags:` adds any further
identity values, `material:` overrides the material, `tooltip-style:` overrides the border.

### Regenerating the catalog

`/royalitems export` writes a fresh, complete classification of every dressable vanilla item to
`catalog-export/` — review the files, then move them into `items/`. Ids owned by `0-overrides.yml` are
skipped so the export never fights your hand-tuned entries.

## When items get dressed

Every supported plain item dresses the moment it is created or acquired: **mined**, **mob drops**,
**harvest**, **craft**, **smith**, **chest loot**, **furnace/blast furnace/smoker output**,
**picked up off the ground**, **when any container closes** (a bazaar, a trade, a chest — the moment
bought or withdrawn items land), and **on join** when `format-on-join` is on.

An item that is already dressed is never re-formatted — but if the definition it was dressed with has
changed since, the same events **refresh** it in place: name, lore, tags and border update; enchants,
damage and everything else the player earned survive. Config edits therefore reach old items through
normal play, with no sweep and no command.

Items are never clobbered: anything with a custom name, lore, enchants, another plugin's persistent
data, or state-as-identity meta (potions, books, heads, banners …) is left exactly as it is.

## Commands & permissions

| Command | Permission | Description |
|---|---|---|
| `/royalitems give <player> <id> [amount]` | `royalitems.give` | Give a formatted item |
| `/royalitems reload` | `royalitems.reload` | Reload all config |
| `/royalitems info` | `royalitems.admin` | Summary of what's loaded |
| `/royalitems inspect` | `royalitems.admin` | Everything about the held item: identity, dress state, and the border verdict with its reasoning |
| `/royalitems export` | `royalitems.admin` | Regenerate the vanilla catalog into `catalog-export/` |
| `/royalitems formatinv <player>` | `royalitems.formatinv` | Dress items a player already owns |

Aliases: `/ritems`, `/rit`. `royalitems.admin` (default: op) grants the rest.

## Text formatting

Any name or lore line is rendered as **MiniMessage** if it contains a tag (`<red>`, `<#ff00ff>`,
`<gradient:...>`), otherwise as legacy **`&`** codes. Both are always rendered non-italic, so items read
cleanly. Mix freely across lines.

```yaml
name: "<gradient:#f7971e:#ffd200>%name%</gradient>"
lore:
  - "&7A legendary blade."
```

## Developer API

RoyalItems registers a `FormattedItemService` on the Bukkit **ServicesManager**. Identity is stored in
persistent data, so a formatted coal is still `Material.COAL` *and* reads as `item_id: coal`.

```java
RegisteredServiceProvider<FormattedItemService> rsp =
        Bukkit.getServicesManager().getRegistration(FormattedItemService.class);
if (rsp != null) {
    FormattedItemService items = rsp.getProvider();

    boolean formatted = items.isFormattedItem(stack);
    String id   = items.getItemId(stack);   // "coal", or null
    String fuel = items.getFuelId(stack);   // "coal", or null
    ItemStack dressed = items.format("coal", 16);
    ItemStack maybe   = items.formatIfSupported(vanillaStack);
}
```

**Soft dependency (no compile-time link):** read the PDC directly, or look up the service by class name
via reflection — the identity keys are `NamespacedKey(royalitems, "item_id")`, `…"fuel_id"`, etc. Add
`RoyalItems` to your `softdepend` so it loads first.

Because a formatted item keeps its `Material`, a plugin that already matches by material (a minion fuel
slot, a shop price, a recipe ingredient) accepts it **with no changes** — the PDC identity is there when
you want stricter matching.

## Compatibility

- **Vanilla:** formatted items keep their `Material`, so recipes, enchanting, repair, trading, and
  shops behave exactly as they did.
- **EcoItems / custom-item plugins:** RoyalItems never dresses an item that already has a name, lore,
  enchant, or another plugin's persistent data — so custom items on a shared base material are left
  untouched. The tooltip borders, meanwhile, cover eco gear too: they read each item's own rarity line
  on the wire and never modify the stored item.
- **Stacking:** a formatted item does not stack with a plain vanilla one of the same kind (different
  data). For tools and armour this is irrelevant (they never stacked). For resources, RoyalItems
  formats at every entry point precisely so stacks stay whole.
